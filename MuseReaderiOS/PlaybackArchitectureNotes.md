# MuseReader iOS Playback Bridge

## Current Playback Path

The Play button now prepares playback through `LiveScoreRenderSession` and `NativePlaybackController`.
The controller starts `AVAudioEngine` after the first short audio chunk is available, then continues scheduling chunked audio from the live score session. It no longer requires a full-score PCM buffer before playback can start.
Audio chunks are generated from MuseScore `PlaybackModel` / `PlaybackEventsRenderer` MPE note events for the active full score or excerpt. The Play path does not export MIDI and does not ask FluidSynth to render a whole MIDI file before playback.

User-facing MIDI export remains in `ScoreDetailView` and is separate from playback.

## Bridge Boundary

The iOS bridge surface is intentionally native and does not expose desktop QML concepts:

- prepare playback for the active `LiveScoreRenderSession`
- play, pause, stop, seek
- report state and time-aware position
- stream time-windowed audio chunks from the active full score or excerpt
- invalidate playback artifacts when score edits or part switches occur
- expose playback measure regions for score following

## MuseScore Dependencies

Required for first iOS playback:

- active `Score` or excerpt selection in `score_render_core`
- `mu::engraving::PlaybackModel` and `PlaybackEventsRenderer` event generation
- MPE `PlaybackData`, note events, arrangement timing, pitch context, and setup data
- playback measure regions from the same repeat/timing map for duration and score following
- FluidSynth as the current event-driven sampler backend, fed directly by scheduled note on/off events
- `AVAudioEngine` output and scheduled chunk streaming on iOS
- revision tokens on Swift-side invalidation to prevent stale chunks from replacing newer playback state

Required for higher fidelity later:

- MuseScore mixer track/channel abstractions
- sound profile and sampler resource selection
- articulation, expression, dynamic, and instrument-change routing
- edit-range invalidation from MuseScore playback cache semantics

Desktop/QML pieces to skip on iOS:

- QML playback toolbar and mixer panels
- desktop audio device preference UI
- project audio export dialogs
- desktop-only module wiring around playback UI state

## Playback Stack Audit

MuseScore proper starts playback in `src/playback/internal/playbackcontroller.cpp`, which coordinates notation playback models with `IPlayback`. `src/framework/audio/main/internal/playback.cpp` owns sequence setup at the audio framework boundary, and `src/framework/audio/engine/internal/engineplayback.cpp` drives engine sequences/tracks. Notation events are generated by `src/engraving/playback/playbackmodel.cpp` and `src/engraving/playback/playbackeventsrenderer.cpp`.

The iOS bridge boundary intentionally skips desktop QML/UI controller objects. It keeps the active render session as the source of truth, asks the active score/excerpt for MPE playback data, maps each MuseScore instrument track to a sampler channel, and streams short PCM chunks to `AVAudioEngine`.

## Removed From Playback Path

- MIDI export before playback
- FluidSynth MIDI player rendering from exported MIDI
- full-score PCM pre-render as the default Play button route
- full-buffer scheduling assumptions

## Practice Mixer

The sliders button beside the metronome opens a bottom sheet on iPhone and a full-width bottom console on iPad. Both layouts place Master and instrument strips side by side with colored vertical faders, pan, Mute/Solo, dB labels, and smoothed live stereo level meters; larger scores scroll horizontally. The iPhone sheet uses narrower channels and a compact header while retaining the reader's original three-zone toolbar: Back is left-aligned, playback stays centered, and Parts, Share, and Edit remain separate controls on the right. Play and Pause share one compact button to make room for Mixer without adding a second toolbar row. Multiple solos are supported, explicit mute takes precedence, and solo evaluation only includes the active playback streams. Metronome output is independent of part solo/mute.

Native event routing retains the master part ID for each sampler channel, including voices, instrument changes, and fallback harmony events. FluidSynth multi-output rendering produces synchronized stereo stems grouped by part. Scores exceeding 128 sampler channels use a second sampler to avoid FluidSynth's modulo output-group collisions; the existing backend's 256 MIDI-channel ceiling remains. Reverb and chorus remain disabled, as before. The mixed stereo buffer is retained for existing audio export callers.

The bridge's `MSRPlaybackAudioData.partSamples` maps stable part IDs (plus `metronome`) to interleaved float32 stereo PCM. Every stem has the mixed buffer's sample rate, frame count, and requested score start time. `NativePlaybackController` applies each part's volume, pan, mute, and solo while summing those stems (vectorized, straight into the player's planar buffer), then schedules that buffer on one `AVAudioPlayerNode`. Using one player avoids first-render skew between several player nodes. A lightweight output tap drives the master meter, while per-part levels come from the same post-fader samples used by the software mix. Their published state is isolated from the score reader to avoid redrawing notation.

Playback streams 125 ms chunks through two queues. Rendered stems are kept up to 3 s ahead (capped at 32 MiB), which absorbs stalls on the shared `LiveScoreRenderSession` actor such as page renders and edits. Only 0.5 s of that is mixed and scheduled on the player, so mixer and metronome changes reach the output within that window. Each buffer is scheduled at an explicit player sample time; if the output queue ever runs dry, the next buffer starts just ahead of the playhead and the silent gap is recorded in `PlaybackTimelineClock`, so score following holds still instead of running ahead of the audio. Playback continues one second past the final barline so the last notes ring out. Pause, stop, seek, revision cancellation, and rendering failure operate on the single output queue. Rendering failures surface through the reader's existing playback error UI.

Loops use the same stream: audio is cut at the loop end and the next chunk is requested at the loop start. The native renderer repositions by rebuilding its synths at the loop start from the cached event sequence, so every pass is sample-identical and memory does not grow with loop length. Short fades at each wrap prevent clicks from notes cut at the loop end.

Native stream reuse: the render core keeps one FluidSynth stream per score revision. Chunk requests that continue where the previous chunk ended reuse it; render blocks stay on an absolute 512-frame grid so consecutive chunks always line up. Seeks keep the extracted event sequence and only create fresh synths, replaying the latest program, controller, and pitch-bend state per channel before a 0.5 s preroll. Parts that `PlaybackModel` leaves silent use the engraving-based fallback extraction on their own channels; all other parts keep model dynamics and articulations.

`ScoreMixerSettingsStore` stores settings locally in UserDefaults by score ID and stable part ID, separately from remembered reader state and notation. Reset clears the mix for the entire score. Newly added part IDs receive defaults. Mixer changes do not modify exported score files or audio exports.
